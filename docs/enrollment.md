# Native server enrollment

The panel supplies one pinned installation command containing only its origin, Machine ID and a 15-minute enrollment capability. The installer runs `caddyctl machine-enroll` with `CADDY_ENROLLMENT_CODE` in its environment. The permanent Machine credential is generated inside that process using 32 cryptographically random bytes; it is never printed or passed to an external process argument. A fresh config is generated by the existing Go configuration initializer in-process. End-user hosts need Bash/curl/tar/CA certificates, with no Go, Python or Docker runtime.

## Claim and retry

Before sending `POST /api/server/enroll`, the CLI writes `/etc/caddy/.machine-enrollment.json` atomically with mode 0600. It contains the immutable panel/Machine/code hash, the candidate credential and completion state; it does not contain the enrollment code. A private file lock serializes concurrent attempts. Network failure, truncated success responses and server errors retry the identical candidate up to three times within a 20-second total budget. Redirects are refused, TLS verification remains enabled, and errors omit remote response bodies, HTTP error URLs and all credentials. Public HTTP origins are supported for existing deployments.

A retry of the identical command reuses the persisted credential, including after the claiming process loses its response. A different panel/Machine identity is refused. A newly generated administrator command may renew an expired pending capability while retaining exactly the same candidate credential and Machine identity. After successful completion, a newly generated enrollment command may rotate the same Machine again. The panel permits replay only while the code is valid and its claimed credential still matches the current Machine credential.

## Existing installations

The installer stages and validates the complete package before claiming. Existing binary identity, native service binding and configuration paths must be known. The CLI validates the exact panel/Machine binding, refuses inline or shared credential keys, acquires the existing credential lock and successfully stages the private replacement before making the HTTP request. Failed claims preserve the original running binary, configuration and credentials. Successful reconnection updates only the selected credential, preserves config.yml and all unrelated credential keys, installs the verified binary pair and restarts the existing service.

Legacy identity overrides in the inherited process or credentials file (for example MACHINE_TOKEN, MACHINE_ID or API_HOST) are rejected before claim because the runtime would otherwise prefer them over the selected YAML binding. Systemd effective units/drop-ins, additional environment files, explicit/passed environment overrides, and OpenRC custom environment files are checked conservatively; custom deployments require coordinated migration rather than silently revoking a working credential. If first-install metadata publication is interrupted after the configuration has been installed, retry repairs the pending metadata before marking enrollment complete.

Unknown Caddy Web Server installations, distribution units, unrelated services, conflicting Machine identities and ambiguous partial installations are refused. No unknown service is stopped or overwritten. The separate connector worker has its own credential file, Unix ownership and service. A matching `/etc/caddy-connect/connect.json` (or legacy `/etc/caddy/connect.json`) causes a concrete preflight refusal before claim; unrelated Machine/Node workers are left alone. CF/MTProxy worker bootstrapping remains separate and is not included in native release packages.

## Interrupted installation

A failed fresh claim leaves only private retry state/locks; running the identical command resumes it. A successful claim whose local credential/config publication was interrupted can resume from the same state and compare any partially published credential with the persisted candidate. Unknown leftover files or incomplete binary/service installations stop automatic recovery rather than guessing ownership. A hard kill can leave a private staging directory; inspect and resolve that named residue before retrying. If the pending command has expired, generate a new command in the panel and execute it on the same Machine; it reuses the private candidate automatically. No permanent token needs to be copied through the panel.

Candidate state and credentials are sensitive local files and belong in any private server backup. A filesystem/service failure after the panel has accepted a claim cannot be rolled back remotely by the installer; the persisted candidate and identical command support recovery without generating a different credential. Online status is Machine connectivity, not per-node readiness.

## Synchronization and tests

Immediately after initial discovery, including zero nodes, the runtime sends machine status. It honors a 10-second discovery interval. Discovery metadata includes optional `kernel_type`; protocol/kernel changes stop the old service and create the proper native kernel. A failed service handle is retried at the next discovery, so corrected saved configuration can recover automatically. Other configuration updates use each node's normal polling reload.

CLI httptest regressions cover local candidate persistence, network and truncated-response retry, process retry, identity/code conflict, redirects, secretless errors, unsafe inline/shared bindings, matching connector refusal and original-config preservation. The runtime test uses the real REST client, a local panel fixture, a zero-node heartbeat, automatic later discovery and real Xray/sing-box loopback listeners, including failure then correction. Shell regressions isolate package/service operations and execute the actual no-prompt main path for fresh install, exact reconnect and refusal. Native release v0.1.3-preview ships the corresponding prepared source, dependency inventory and original notices through the existing release workflow.
